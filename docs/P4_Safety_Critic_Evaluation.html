The Trust Layer

P4 ensures that the system does not merely generate an answer — it verifies that the answer is safe, grounded, policy-compliant and measurable.

Safety Layer

PII redaction

WHAT: Strip emails, phone numbers, credit-card numbers and password-like secrets before they reach logs, answers, or bundles.

WHAT CODE: redact() in app/safety.py.

WHY: Prevents sensitive data from propagating through the model, the API, or the handoff bundle.

EXAMPLE: jane.doe@example.com → [EMAIL], 4111 1111 1111 1111 → [CARD].

Secret detection

WHAT: Detects API keys, bearer tokens, reset-link requests and password exposure attempts.

WHAT CODE: regex patterns and asks_for_secret().

WHY: A customer may ask the model to reveal a secret; the safe path is to refuse and redirect to a secure action.

EXAMPLE: Show me my API key is blocked; How do I rotate my API token? is allowed.

Cross-account authorization

WHAT: Customer identity is taken from the X-Account-Id header only.

WHAT CODE: other_account_requested() in app/safety.py, enforced by the pre-check gate in app/graph/nodes.py.

WHY: We must not trust a message that says I am A1004 if the header says A1001.

EXAMPLE: Header: A1001; message: Show me invoices for A1004 → refused.

Promise detection

WHAT: Detects statements like “your refund has been issued” or “I have credited your account”.

WHAT CODE: makes_promise() in app/safety.py, used by critic and escalation policy.

WHY: The model cannot actually approve a refund or change an account; this check prevents unauthorized promises.

EXAMPLE: Your refund has been issued. triggers a policy risk and forces revision or escalation.

Log redaction

WHAT: PII is redacted not just in responses, but in log output too.

WHAT CODE: RedactingFilter and setup_logging() in app/safety.py.

WHY: Response redaction alone is not enough; logs are often the accidental leak path.

EXAMPLE: A log line containing an email gets rewritten to [EMAIL] before it is written.

Bundle redaction

WHAT: The final handoff bundle is scrubbed before storage.

WHAT CODE: build_bundle() in app/escalation.py plus redact_obj() in app/safety.py.

WHY: Human handoffs need details, but not raw customer PII or secrets.

EXAMPLE: A summary may retain “charged twice” but not the customer email or full card data.

Refuse branches

  • Secret request: asking for an API key, password, reset link or email on file is refused.

Allowed examples

  • Allowed: “I forgot my password, help me reset it.”
  • Allowed: “How do I rotate my API token?”
  • Blocked: “Show me my API key”, “What is my password?”, “Send the reset link here”.

Cross-Account Authorization

Rule

The authenticated account comes from the HTTP header X-Account-Id only. The message body is never trusted as an authority source.

In the repo, this logic is enforced in app/safety.py and the pre-check node in app/graph/nodes.py.

Example

Header: A1001
Message: "Show me invoices for A1004"
Result: REFUSED

So the system does not trust the identity supplied inside the user text. It only trusts the signed-in account header.

This also covers company and email-based checks. If a message asks for data tied to another company or email on file, the system refuses as a cross-account or cross-company request. This is a direct guardrail against account leakage.

Secret Request Protection

Blocked

  • Show me my API key
  • What is my password?
  • Send the reset link here

Allowed

  • I forgot my password, help me reset it.
  • How do I rotate my API token?
WHY this distinction exists: a reset request can be safely handled by the tool and by sending the reset message to the email on file. A key or password is a secret, and revealing it is a security incident. The code intentionally differentiates “reset me” from “show me the secret”.

Promise Protection

LLM draft:
"Your refund has been issued."

↓ deterministic promise scan

POLICY RISK

The repository explicitly detects phrases like “refund has been issued”, “I have credited your account” and “your account has been upgraded” using makes_promise() in app/safety.py.

Why: the LLM cannot authorize or execute a refund, credit or plan change. That is a policy decision and an action the system cannot safely allow without a human review. The check protects against confident but unauthorized claims.

WHAT: Logs, console output and file output are all redacted before persisting.

WHAT CODE: RedactingFilter and setup_logging() in app/safety.py.

WHY: Response redaction is necessary, but insufficient. Logs often end up in support tickets, CI output, observability tools or developer terminals.

WHAT: The critic reviews the candidate answer and the evidence it was built from.

WHAT CODE: The critic prompt and validation logic live in app/llm.py and are applied by the critic node in app/graph/nodes.py.

WHY: A grounded answer must be supported by retrieved documentation and tool results, not just plausibly written prose.

HOW: The critic returns a Critique object with groundedness, coverage, PII risk, policy risk, issues and decision. It is useful because it scores content quality, but it is not trusted to make the final decision.

This repository uses a hybrid model: the LLM provides a language-quality score, while deterministic code adds exact checks that cannot be left to model discretion.

Important idea: The LLM evaluates language quality; deterministic code catches conditions that must be exact.

Unsupported Terms

Example: “Does CloudFlow integrate with SAP Ariba?”

Retrieved evidence: no SAP or Ariba evidence in the retrieved knowledge base.

System behavior: do not confidently answer, and do not present a guessed answer as fact. This is a controlled guardrail in unsupported_terms() inside app/graph/nodes.py.

Why it matters: it prevents hallucinatory product claims and keeps the pipeline honest when the KB does not support an answer.

Policy Gate

Critique + intent + tool state + policy
                ↓
             decide()
          /      |       \
       ANSWER  REVISE  ESCALATE

WHAT: The final “answer or escalate” decision is made in code, not by the LLM.

WHAT CODE: app/escalation.py and the decide node in app/graph/nodes.py.

WHY: Code is predictable, auditable and testable; the model should not be the final arbitrator of whether a human must take over.

Escalation reasons included in code:

  • billing dispute
  • legal matter
  • account deletion
  • security incident
  • explicit human request
  • repeated contact
  • tool failure
  • KB gap
  • unresolved conflict
  • low groundedness
  • promise made

WHY it exists: prevents infinite loops, limits latency, controls cost, preserves safety, and gives the system a guaranteed endpoint.

This logic is implemented in decide() in app/escalation.py and enforced by app/graph/nodes.py.

Policy Registry

The system reads key thresholds from the SQLite policy registry instead of hard-coding them. This was explicitly designed to make policy changes easy and auditable.

  • critic_min_groundedness
  • escalation_sla_hours
  • repeat_contact_threshold
  • min_relevance

Why this matters: changing a policy value can change runtime behavior without rewriting the decision logic. The implementation pulls these values at runtime from the policy_registry table.

What I Should Say to a Judge

10-second answer

“I worked on the trust layer of InsightDesk: safety, critic, escalation and evaluation.”

30-second answer

“Our safety layer protects PII and secrets, enforces account identity from the header, and blocks unauthorized promises. The critic scores groundedness and coverage, and the policy gate decides whether to answer, revise once or escalate. Evaluation then runs the labelled scenarios and reports the exact metrics.”

2-minute answer

“A request enters the pipeline. First, the safety pre-check redacts secrets and blocks another-account or secret requests. Then the classifier decides the intent. The system retrieves docs and tools, composes a draft, and the critic scores it. If the answer is weak or policy-risky, the code either revises once or escalates. For an escalation, the system creates a handoff bundle with evidence and unresolved questions. Finally, eval/run_eval.py runs the labelled cases and records the metrics in eval/report.md.”

Likely Judge Questions

  1. Why not let the LLM decide escalation? Because the LLM can be wrong or manipulated; code is deterministic, auditable and policy-based.
  2. Why use regex for PII? Because it is fast, explainable and works before a model sees the message.
  3. Why one revision only? It prevents loops, reduces cost and gives a safe terminal rule.
  4. Why do we need a critic if we already have retrieval? Retrieval finds evidence, but the critic checks whether the answer is actually grounded and whether the question is supported.
  5. What if the critic itself is wrong? The final answer still depends on code checks, policy registry thresholds and a human handoff path when needed.
  6. How do you prevent cross-account leakage? By trusting only X-Account-Id and refusing any message that references another account or email.
  7. How do you test safety? With explicit tests in tests/test_safety.py and evaluation cases in the eval suite.
  8. How do you know the system is grounded? By checking retrieved evidence, citations and scored review in the critic step.
  9. Why store policy in a registry? So thresholds can change without changing Python logic; the system reads the registry each run.
  10. What is currently incomplete? The checked-in mock run has one answer-content miss (E-M4-03); retrieval was updated to include more failed-payment guidance, but that fix still needs an evaluation rerun. Critic agreement is pending independent human labels, and live Ollama evaluation remains to be run.
